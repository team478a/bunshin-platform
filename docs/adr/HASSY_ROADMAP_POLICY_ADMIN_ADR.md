# ハッシーのロードマップ達成条件管理

状態: 実装済み。検証結果は実装報告とPRを参照。main 0775e1b2を基準とする。本番変更は行わない。

## 判断

- 共通Applicationの進捗評価は変更せず、ハッシーの3つの利用実績目標と任意の紹介目標をWebのProduct Policyで定義する。固定5段階、FACT条件、機能権限は維持する。
- 保存・同時更新制御・本部/OEM認可・冪等性・監査を既存SNS提案設定から共通のManaged Feature Policy Repositoryへ抽出する。SNSの意味と判定はSNS側に残す。
- 既存GroupFeaturePolicyの保護された_managedPolicies内にhassyRoadmapPolicyを保存する。SOCIAL.ACTIVITY_SUPPORT行を再利用するが、同機能の有効化や支援提案条件とは独立した名前空間とする。新規テーブル・migration・イベントは追加しない。
- 明示的なHASSY templateのサービスだけを対象にし、保存時にもDBで再確認する。他サービスにHASSY既定値を適用しない。
- 本部はサービスごとの基準を設定する。OEMは本部設定後に、各利用実績の目標を基準以上にできる。紹介目標は本部が許可した場合だけ利用でき、OEMでは無効化または本部以上の目標にできる。本部の後続変更は実効値へ反映する。
- 紹介目標はSTEP 5の任意の進捗表示。基本SNS機能、他の達成判定、利用権限、確定特典の条件として使わない。設定変更で現在の進捗表示は再計算するが、原イベント・紹介成果・特典・採用済み支援を変更しない。
- 未設定は従来の目標(生成1、判断1、活動3日、紹介目標なし)。不正な保存設定は黙って既定値へ戻さずロードマップ取得を失敗させる。SNS本体の操作は独立する。
- 段階追加・並び替え・FACT条件の編集・特典付与設定は今回の範囲外。

## 検証条件

純粋な条件検証と進捗反映、他template拒否、他OEM拒否、権限取消、revision競合、同一要求再送、同一行のSNS設定保存との共存、監査、スマートフォン操作を検証する。
