# 通常設定の理由入力を減らし、重要条件の理由を保持する

日付：2026-11-03。対象：管理運用簡素化PR-2A。監査・計画は`ADMIN_UX_OPERATION_AUDIT.md`と`ADMIN_SIMPLIFICATION_IMPLEMENTATION_PLAN.md`。本番変更の承認を意味しない。

団体プロフィールのreasonは検証されるだけで保存されない。週次配信のreasonは既存UIが定型文を入れる。サービス設定は通常の文章・見た目・時刻と、登録受付・法務参照先・取得情報・AI/メディア利用条件が同じ保存経路にある。

本PRでは次を選ぶ。

- 団体プロフィールは未使用のreason検証・入力を撤廃する。旧FormDataのreasonは無視して受理する。認証と団体管理者の確認は維持する。
- 週次配信はサーバーが既存の定型reasonを補完する。旧clientの有効なreasonも受理する。
- サービス設定の通常変更はサーバーがreasonを補完する。登録受付・法務参照先・収集情報・提供方式・AI/メディア利用条件の変更では、既存の理由入力を保持する。判定はフォーム専用の小さい共通関数をUIとHTTPで再利用し、HTTPも現在の認可済み設定と照合する。
- Application全体のreason必須条件、Repositoryの認可、ServiceConfigurationAuditのactor/対象/before/afterと業務更新の同一transactionは変更しない。料金・権限・秘密情報の別APIも対象外。

全reasonの無条件任意化は重要条件の記録を弱めるため選ばない。通常変更にも定型文の手入力を求める案、汎用承認エンジンや新規監査テーブルも選ばない。追加確認ダイアログは導入しない。

今回の判定は新しい権限・同意・実行許可ではない。同時更新のCAS、変更していない項目の書込削減、全snapshotの合理化は後続の専用PRで扱う。新しいreasonの有無だけで、古いclientの変更を拒否する破壊的な移行はしない。
