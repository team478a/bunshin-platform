# OEM事業者向け決済運用画面 実装報告

## 1. 調査した内容

- `ProgramPurchase` に購入者、金額、購入状態、入金・期限切れ・返金日時が保存されていること
- `PaymentWebhookEvent` にStripe通知の処理状態とエラー分類が保存されていること
- 運営団体の所有者・管理者、またはシステム管理者だけが決済設定画面を開けること
- 購入とWebhook通知を `workspaceId` で運営団体ごとに分離できること

## 2. 変更したファイル

- `apps/web/app/(app)/organizations/[workspaceId]/payment/page.tsx`
- `apps/web/src/payments/payment-operations.ts`
- `apps/web/test/organization-payment-page.test.ts`
- `apps/web/test/payment-operations.test.ts`

## 3. 主要な設計判断

- 新しい集計テーブルは作らず、既存の購入台帳とWebhook台帳を利用する。
- すべての検索に画面の `workspaceId` を指定し、別の運営団体の購入情報を表示しない。
- 決済完了総額は、入金を一度確認できた購入の金額合計を「返金前」と明記する。
- 部分返金額は現在の台帳に金額項目がないため、総額から差し引かない。
- 運営者が最初に判断できるよう、Webhook失敗、支払い待ち、問題なしの順で案内を表示する。
- 最新20件の購入と最新10件の失敗通知に表示を絞り、スマートフォンでも既存の横スクロール表で確認できるようにする。

## 4. 実行した検証

- 決済運用表示の単体テスト
- 決済設定画面の組織分離に関するソース検証
- WebアプリのTypeScript型検査
- Prettierによる変更ファイルの整形

## 5. 未解決事項

- 部分返金額はStripe通知のメタデータに記録されるが、専用の金額カラムがないため画面集計には含めていない。
- 失敗Webhookの再処理機能は今回の対象外。画面では検知と問い合わせ案内まで行う。
- 期間指定、CSV出力、購入者検索は購入件数が増えた段階で追加できる。

## 6. 次Phaseへ進める条件

- 本番Stripeで購入、期限切れ、全額返金を各1件実行し、運営団体の画面に反映されることを確認する。
- 必要に応じて、失敗Webhookの安全な再処理と部分返金額の台帳化を別の作業単位で行う。
