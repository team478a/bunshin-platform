## ハッシー: 観測と評価の差分

| 問題             | 既存正本・検査                                        | 追加する最小評価                                                           | 限界・停止条件                                               |

| 別企業へ似た提案 | businessProfile、personalization signals、EVO混入負例 | 他条件固定で企業/顧客/目的を変え、企画・根拠の意味的差と登録事実整合を評価 | 生原稿の他OEM共有なし。合成対照から開始、表現差だけは不合格  |
| 企業情報未反映   | Provider入力のbusinessProfile/approvedStrategy        | 情報あり/なし/変更の対照。何を使い、どの提案判断が変わったかを人間確認     | Providerの「使った」自己申告だけではPASS不可                 |
| 採否履歴未反映   | FEEDBACK_HISTORY、MissionDecision/Feedback            | 履歴あり/なし、長文拒否/用途不一致等の対照                                 | 不採用理由を人格・事実として永続共有しない                   |

| 初期設定離脱     | 登録Funnel、onboarding段階                            | 同一cohortの開始/完了/観測窓、欠測/通信失敗を分離                          | Landing匿名IDは仮名。本人/Serviceとの無断結合なし            |
| 生成後未採用     | Mission/Activity/Decision/PostRecord                  | 生成成功→閲覧→決定→実投稿の別率                                            | 採用=投稿成功ではない。自己申告成果とSNS実測を区別           |

| ---------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 目的に合わない課題     | Goal confirmation/Plan revision/Definition/Assignment | 目的と仕事場面の合成対照、参照版・未確認目的の扱い                                                       |

AIの回答・高score・課題完了を本人能力の証明にしない。AIが完成品を代行するモードへ戻さない。回答不足・外部操作未確認・題材参照欠落はREVIEW/UNKNOWNのまま。少数受講者をOEM横断で合算しない。

## 検出ルールの最初の提案

固定codeによる候補だけから開始する。閾値は未承認であり運用設定にしない。

- 技術: 既存24h失敗3件ルールを再利用。ただしProvider総attempt・欠測率と併記し、自己申告と別根拠にする。
- ハッシー: 同Bunshinの連続3回不採用を要確認候補案とする。対象期間・閲覧/決定母数を明示し、改善/解決を自動認定しない。
- マナベル: 評価待ち・失敗・本人実践未確認を別状態に集計。単なる未提出を原因確定しない。
- 個人単位の支援判断は本人のscope内に留める。管理者統計は既存の少数非表示条件を維持。少数のP0事故は限定権限の事故対応経路で扱い、統計の匿名性基準を緩めない。

## 重複開発を避ける禁止事項

新しい課金台帳、全ログ複製、別Queue、全サービス共通人格/Memory、自動Prompt本番編集、自動モデル切替、独立した再現能力採点器を先行追加しない。既存未接続機能の接続PRと、コード生成RunnerのPRを分ける。
