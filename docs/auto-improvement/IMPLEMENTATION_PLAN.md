# Phase別実装計画

## 結論と見積前提

まずPhase 1-Aの**既存記録の読取専用統合と欠測表示**を承認対象にする。Phase 0は本PRで完了する調査範囲。Phase 2以降、本番設定/外部AI/課金/DB変更は承認されていない。

工数は既存構造を理解した開発者1名の概算人日。レビュー・試験・文書を含むが、顧客検証待ち・運用観測期間・契約・環境準備待ちは除外。成果が基準に届かなければ停止/再見積する。並行実装を前提にせず、合計40〜71人日は全自動化を先に作る約束ではない。

## 最初のPR単位

### Phase 1-A: 4〜6人日（Phase 1内数）

追加DB/外部AI/新OSSなしで、既存公開Portを使うread-only観測契約と合成試験から着手する。

1. E4/E8の既存Readerを再利用し、ハッシー採否/投稿・支援/Photoの限定summaryを用意する。
2. E7の管理用投影からマナベルAdapterを作る。本文・個人結果・consultationを取得しない。
3. 母数・source/version・coverage・取得上限・UNKNOWN・少数非表示の契約をそろえる。率を作れない記録は件数だけでなく「未判定」と表示する。
4. cross-scope/移管/権限失効/期限/欠測/0件/limit+1/余剰fieldの負例、外部fetch禁止を検証する。

受入時はコードの契約までで、本番自動収集完了とは呼ばない。個別管理者向けpage接続は1-B（2〜3人日）、技術ログ相関/本番確認準備は1-C（2〜4人日）へ分ける。source環境帰属・記録捕捉が不足なら必要最小の追加設計をレビューし、無条件にschemaを追加しない。

### Phase 2-A / 3-Aの開始制限

2-Aは合成Evidenceだけの人手レビュー案作成。3-Aは合成Issue1件の人手起動Dry Run、GitHub公開前までを先に検証する。外部AIまたはGitHub writeを行う段階ごとに、費用・送信先・許可repo/branch・停止責任者の承認が必要。

## 評価受入条件

ハッシー: 登録情報が企画の判断へ意味的に反映、7日系列で異なる疑問/具体例へ展開、不採用理由を次回へ反映、別企業混入なし。対照条件・期待理由を人間が先に固定する。生成AI自身の自己採点だけにしない。

マナベル: 仕事/目的に沿った課題、過去実践に基づく難易度/支援、回答不足を合格にしない、AI完成品≠本人能力、支援を減らした本人再現を独立観測。EVO-05既存契約を接続し、二重の評価器を作らない。

修正PR: CI成功だけでは採用しない。仕様整合、scope、回帰、実再現、差分最小、費用、rollback、前後証跡を人間が確認する。外部研究benchmarkの成功率をbunshinの修正成功率に換算しない。

## 運用移行と費用

本番から改善するには全自動修正より先に、通常登録での少数利用、正しい受付/エラー/母数観測、人間による週次レビューが必要。招待制への変更は計画しない。既存の機能・契約・学習安全条件を迂回する登録やPilot開始を本PRで行わない。

費用式: `分析run数×分析token単価 + 修正attempt数×修正token単価 + 評価ケース×反復数×推論単価 + sandbox実行時間 + 保存/転送/運用費`。API単価・クラウド月額・為替は未見積。OSS無料ライセンスでも運用費0ではない。

承認候補の初期上限案: 1 case最大2修正attempt、1 attempt最大30分、同時1run、1日最大3cases。金額は本部がUSD micro等の正確な通貨・単位で承認し、未設定ならdispatch禁止。費用UNKNOWNで予約を解放して再試行しない。合成dry runでは外部AI費用0円を維持する。

## 最終gate

[承認事項](DECISION_REQUIRED.md)の決定後、Phase 1-Aだけを別branch/PRで実装する。Phase 2〜5、契約、secret登録、production反映、実課金、実送信を包括承認としない。監査PR提出後は次の指示を待つ。
