# ワタシワークス 活動継続機能 再基準化

## 1. 目的

本文書は、`watashi_kikakushitsu_activity_spec_v1_0.docx`を最新`main`の実装に照らし、新たな活動継続機能の正本、既存機能の再利用範囲、実装順序と停止条件を定める。

ユーザー向けサービス名は「ワタシワークス」とする。`Bunshin`はAI分身のDomain用語として維持し、DB、API、型名、環境変数、監査Event名はブランド変更のために改名しない。

## 2. 成功条件

活動継続機能の成功は、画面を開く回数ではなく、ワタシワークスの提案が準備と実際の投稿へ繋がることとする。

最重要KPIは「7日間にワタシワークスの提案を使って3回以上投稿したユーザー率」とする。

利用行動は次の4段階を混同せずに計測する。

1. 利用継続: 通知から開いた、内容を確認した
2. 投稿準備: 採用した、文章や画像用指示をコピーした
3. 実行: 投稿完了を報告した
4. 結果: 本人が反応や成果感を任意入力した

## 3. 最新mainの実装監査

### 3.1 そのまま再利用する正本

| 領域             | 既存の正本                            | 方針                                   |
| ---------------- | ------------------------------------- | -------------------------------------- |
| 当日の提案       | `DailyMission` / `MissionContent`     | 新しい`daily_contents`を作らない       |
| 採用判断         | `MissionDecision`                     | 確認・コピー・投稿と分離する           |
| 行動履歴         | append-only `MissionActivity`         | 新しい汎用`activity_events`を作らない  |
| 投稿完了         | `PostRecord` / `POSTED` Activity      | 新しい`post_reports`と二重保存しない   |
| 投稿後評価       | `MissionFeedback` / Feedback Activity | 本人申告のOutcomeとして維持する        |
| LINE通知設定     | `LineNotificationPreference`          | 時刻、timezone、頻度、停止を再利用する |
| LINE配信         | 既存Job、Delivery、Attempt、Retry     | 新しい配信基盤を作らない               |
| LINEからの復帰   | 短期・一回限りstateとverified session | ユーザーIDをURLへ平文で含めない        |
| 継続・Funnel集計 | 既存の検証指標と管理画面              | 既存Raw Eventから再計算する            |

### 3.2 追加候補

- 本人が押す「内容を確認しました」の行動種別
- 「今日は休む」の状態と行動種別
- 週間進捗と累積進捗のRead Model
- 発信ステップと達成バッジ
- バッジ条件と活動ルールの版管理
- 休眠判定と復帰候補の管理

## 4. 行動の責務分離

| 行動                    | 意味                                 | 進捗への扱い                     |
| ----------------------- | ------------------------------------ | -------------------------------- |
| `VIEWED`                | 本人認証後にMissionを正常表示した    | 閲覧のみ。本人の確認とみなさない |
| `CONFIRMED`             | 本人が「内容を確認しました」を押した | 利用継続の進捗に使う             |
| `ACCEPTED` / `REJECTED` | 採用判断                             | Preferenceとして扱う             |
| `COPIED_*`              | Clipboardへの成功                    | 投稿準備の進捗に使う             |
| `POSTED`                | `PostRecord`が正常作成された         | 実行進捗と最重要KPIに使う        |
| `FEEDBACK_*`            | 投稿後の本人評価                     | OutcomeとPreferenceを混同しない  |
| `RESTED`                | 本人が今日は休むと選んだ             | 負の評価や減点に使わない         |

`CONFIRMED`と`RESTED`は候補名であり、実装PRで既存Enumとの整合を確認して最終決定する。Mission lifecycle、Mission Decision、Mission Activityを一つの状態機械へ統合しない。

## 5. 日付と冪等性

- DBの時刻はUTCで保存する。
- 日次・週次判定に使った`localDate`、`timezone`、週開始日を固定保存する。
- 初期timezoneは`Asia/Tokyo`、週開始は月曜日とする。
- 一意性は`userId + localDate`のみにしない。`workspaceId`、`userId`、`bunshinId`、`dailyMissionId`を同時に検証する。
- Group Campaignの場合は`groupId`と`membershipId`も再検証する。
- 同じ操作の通信再送は同じ結果を返し、Activity、進捗、バッジを二重計上しない。

## 6. 進捗Read Model

進捗はRaw EventとPostRecordから再構築できる派生データとする。当日や週間画面の応答を安定させるために集計rowを持つ場合も、同じEventから再計算する修復手段を必須とする。

最低限のView Modelは次を返す。

- 今日の状態: 未確認、確認済み、準備中、投稿済み、休み、対象外
- 今週の確認日数、コピー日数、投稿日数
- 週間目標までの残り回数
- 累積投稿数、最終活動日、利用日数
- 現在の発信ステップと獲得バッジ

「週に3回確認」は優しい利用継続目標として表示できるが、投稿継続KPIの代わりにはしない。

## 7. 発信ステップとバッジ

- ステップは原則として下げない。
- バッジは条件を満たしたとき1回だけ付与する。
- 条件と表示文言に`ruleVersion`を持たせ、過去の付与結果を後から書き換えない。
- 合計点、金銭価値、換金、報酬確約として表示しない。
- 順位、他者比較、連続日数が途切れたときの罰をMVPに入れない。
- SOCIAL専用Enumに固定せず、`SOCIAL`、`BLOG`、`GROUP_CAMPAIGN`、`IMAGE_GENERATION`などの安定した機能Keyと関連付けられる構造にする。
- Group向けルールは、Platform AdminがGroupへ許可した機能範囲内でのみGroup Managerが利用できる。

## 8. 休眠と復帰

- 「今日は休む」はペナルティにせず、過去実績やバッジを失わせない。
- 3日、7日、14日、30日の候補値は固定仕様にせず、版管理された運用設定とする。
- 休眠判定は新しい正本にせず、最終有効活動日から派生する。
- 配信頻度を自動変更する場合は、本人同意、現在の通知設定、Quiet Hours、全体停止、月間配信上限を必ず再検証する。
- LINEブロック、友だち解除、配信停止中のユーザーへ復帰Pushを送らない。

## 9. ユーザー体験

スマートフォンの「今日やること」を中心に、次を表示する。

- 今日の投稿案
- 「内容を確認しました」
- 採用・今回は使わない
- 形式別コピー
- 「投稿しました」
- 「今日は休む」
- 今週の実績と次の小さな行動

ボタンは短時間の連打を抑止し、成功・保存完了・コピー完了を文字で明示する。専門用語、減点、失敗扱い、過度な競争表現を使わない。

## 10. 管理画面

### Platform Admin

- ルール版、週間目標、ステップ、バッジ、休眠日数の管理
- 配信失敗、集計遅延、イベント欠損の確認
- 全体KPI、Group別KPI、テスト利用者除外
- 理由付き手動修正と追記型Audit Log

### Group Manager

- Platform AdminがGroupへ許可した範囲での目標・バッジの選択
- 自Groupの同意済みACTIVE Membershipの集計だけを確認
- 他Group、参加者の通常Mission本文、個人Memory、Knowledge、Feedback詳細を閲覧しない

## 11. データ保護

- Activity metadataへ投稿本文、画像指示文、個人Memory、Knowledge、LINE user ID、トークンを保存しない。
- 投稿URLと任意の成果情報は目的を明示し、未入力でも主要導線を完了できるようにする。
- Group管理者には必要な集計だけを返し、個人の通常投稿履歴を閲覧させない。
- 退会時は既存の匿名化・削除実行計画に従い、新しい活動resourceも分類表に追加する。
- 行動データの広告・推薦利用は、明示した利用目的と必要な同意の範囲外で行わない。

## 12. KPI

### 最重要

- 7日間に3回以上投稿したユーザー率

### Funnel

```text
LINE通知成功
-> Web表示
-> 内容確認
-> 採用
-> コピー
-> 投稿報告
-> 結果入力
-> D7 / D30 Active
```

### 補助指標

- LINE通知からWebへの遷移率
- 確認から採用への移行率
- 採用からコピーへの移行率
- コピーから投稿への移行率
- 週に3回確認したユーザー率
- 休眠復帰率
- LINEブロック・配信停止率
- テーマ、支援レベル、SNS、投稿形式別の投稿完了率

## 13. 必須テスト

- 他Workspace、他User、他Bunshin、他Group、他Membershipの活動を参照・更新できない
- ダブルタップ、通信再送、複数端末で二重計上しない
- timezoneの23:59 / 00:00、週の切替、夏時間を誤判定しない
- VIEWEDだけでCONFIRMED、ACCEPTED、POSTEDに進めない
- 「今日は休む」で過去実績を削除・減点しない
- バッジを同じ条件で二重付与しない
- ルール版更新後も過去のスコア・バッジを書き換えない
- 集計の削除・破損後にRaw Eventから再構築できる
- LINE配信失敗中でもWeb上のMission確認と活動記録を使える
- 小型スマートフォン、文字拡大、低速回線で横スクロールや操作不能を発生させない

## 14. 実装順序

### J0: 再基準化

- 本文書
- RoadmapとDecision Logの更新
- 実装コード、Prisma Schema、Migrationは変更しない

### J1: Activity Continuity Core

- 確認・休みの行動定義
- 冪等な記録Use Case
- 週間・累積Progress Query / Read Model
- Workspace / User / Bunshin / Group isolation

### J2: ユーザー体験

- 今日の確認・休み
- 活動カレンダー
- 今週あと何回
- 完了表示と再訪時の状態保持

### J3: Step / Badge / Return

- 発信ステップ
- バッジ条件と付与
- 休眠判定と復帰表示
- 必要最小限のLINE連携

### J4: Operations / Validation

- ルールと閾値の管理画面
- ユーザー・Group別進捗
- Funnelと最重要KPI
- テスト利用者除外
- 監査、監視、CSV出力

## 15. J1開始前の人間確認

1. 「内容を確認しました」をVIEWEDと別の明示行動とするか
2. 週間利用継続目標の初期値を3回とするか
3. 活動目標とバッジを一般利用とGroup利用で共通化するか
4. 休眠日数3 / 7 / 14 / 30を初期運用値とするか
5. 任意のSNS数値、投稿URL、問い合わせメモの保持期間と管理者表示範囲
6. 初回検証をFREE一般ユーザーで行うか、許可したGroupで先行するか
