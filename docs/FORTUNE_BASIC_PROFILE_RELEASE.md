# 月と星のオラクル 基本プロフィールの本番移行

対象は `watashi-fortune`。開発時の設計は[基本プロフィールのADR](adr/FORTUNE_BASIC_PROFILE.md)、隔離環境の準備は[占いの隔離E2E](FORTUNE_ISOLATED_AUTH_E2E.md)を参照する。

## スキーマ変更の影響

`20261123123000_fortune_basic_profile` を追加する。既存の占い参加者にはNULLを許す案内完了日時を1列追加し、空の基本プロフィール用テーブルを新設する。既存のプロフィール、鑑定、会員情報のバックフィルはない。会員取消時に専用テーブルから値を消すトリガーを追加する。スキーマ変更では対象テーブルのロックを取るため、適用前にDBの負荷と既存ロックを確認する。

## 反映と確認の順序

1. PRの順次統合後、対象SHAとGitHub Actionsの `verify`、`database` を確認する。隔離環境で既存マイグレーションからの適用とプロフィールE2Eを実行する。
2. 承認前に本番のマイグレーション履歴と既存スキーマを参照し、対象SQL、影響範囲、適用対象SHAを報告する。
3. 承認後、対象SHAの既存の本番移行手順でスキーマを適用する。履歴と `pnpm db:assert-ready` の確認後にアプリを反映する。公開設定時点までは基本プロフィールの収集を停止した状態で、既存利用者の無料鑑定と履歴を確認する。
4. 初回画面の案内と個別化同意の説明を運営側で確認する。対象Serviceの「ヒアリングとAI案内役の設定」で承認された項目だけを有効にする。
5. テスト参加者で、年齢確認、未入力のまま無料鑑定、入力からの編集と削除、同意撤回後の無料鑑定と履歴、別Serviceでの分離を確認する。iPhone Safari、Android Chrome、LINE内ブラウザで日付入力、保存、スキップと390px前後の見切れを確認する。
6. 問題があれば、先に管理画面で収集を停止する。保存済みの項目の削除・撤回を本人設定から継続できる。アプリの切り戻しは既存の手順に従い、新規テーブルに保存済みの値を確認した上でスキーマの扱いを判断する。

## Go／No-Go

CIと隔離E2Eが通り、本番移行・収集について個別の承認があり、対象端末で確認工程を通過した場合に公開可。確認が残っている間は収集停止を維持する。
