# 日常業務を中心にした管理画面の再設計

作成日：2026-11-03 JST。監査基準SHA：`7d397821b144361dcf5643dc92ce4ac95ebcb334`。本書は画面・操作の提案であり実装済み画面ではない。対象の現状は[監査](ADMIN_UX_OPERATION_AUDIT.md)、制御方針は[分類](ADMIN_RESTRICTION_SIMPLIFICATION_PLAN.md)を参照。

## 1. 管理の文脈を先に決める

本部管理、団体/OEM管理、Service管理は認可の境界が違う。外観と業務分類をそろえても、データ・操作権限を統合しない。現在の管理対象名を常に上部に表示し、本部からサービス管理へ移ったことを明示する。

現在の`AppShell`は`/admin`に本部sidebarを適用する。Service管理は別のPublicShellと長いメニューである。まず既存routeへのリンクを再配置し、Service画面へ全本部sidebarを持ち込まない。共通コンポーネントは表示分類・見出し・保存状態など、実際に同じものに限定する。

## 2. 基本の5分類

| 分類                 | 本部                                                        | Service管理                                                                      | 団体/OEM管理                                                     |
| -------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| ダッシュボード       | `/admin`、運用通知の要点、全体障害                          | `/s/{slug}/manage`、会員数・稼働・要対応・主要実績                               | `/organizations/{workspaceId}/manage`の概要と所属サービス        |
| 会員・契約管理       | users、organizations、groups、請求・入金・契約              | members、programsの参加枠、本人への通常案内                                      | 既存の運営者招待、所属Group、usage/payment。許可された契約範囲内 |
| 配信・コンテンツ管理 | コンテンツ運用、画像/動画の状態                             | LINE一斉配信、templates、knowledge、post-approvals、video-deliveries等の該当機能 | 所属サービスへのリンク。共通設定を二重保存しない                 |
| サービス設定         | services、承認済み初期設定の選択                            | settings、lineの配信方針、email、recommendations、roadmap等                      | 団体情報・所属サービスの設定。サービス値はサービス画面で管理     |
| 詳細管理             | audits、権限、API接続、法務、退会・削除、公開Gate、原価詳細 | 接続の技術情報、詳細履歴、学習準備の来歴、保持/削除等の該当機能                  | 団体内の詳細履歴・技術接続。権限がない本部項目は表示しない       |

`legal`は詳細管理に置いても、未公開法務文書の要対応リンクはダッシュボードへ出す。契約画面・課金・外部送信の重大な警告は詳細に隠さない。変更履歴を通常操作で毎回開く必要はなくす。

サービスによって3〜5分類に減らしてよい。空のカテゴリは表示せず、現在の26メニュー候補を単に5列へ並べ替えるだけにしない。既存画面の直接URL、auth return、APIは維持する。

## 3. サービス別の表示

| 対象             | 日常の優先項目                                             | 詳細へ寄せる項目                           | 表示しないもの                                               |
| ---------------- | ---------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| ハッシー         | 投稿/配信状況、会員対応、必要な投稿確認、SNS支援提案と目標 | 個別化根拠、生成経路、Feature/HQ設定の来歴 | 研修専用の準備手順、無関係な占い機能                         |
| マナベルスタイル | 受講者、研修状況、学習設計の要対応、必要なAI利用状況       | Pilot技術設定・実行許可の詳細・原価/保持   | SNS専用のFAQ不足・商品投稿の不足を研修開始の必須条件にしない |
| その他/OEM       | 実際に付与されたProgram/Featureと許可内の設定              | 本部条件の参照、技術接続、監査             | ハッシー固有の成長目標・質問・閾値を自動適用しない           |

この投影は既存のService context、hasAiTrainingServiceProgram、Feature、service-management-navigationを再利用する。表示可否は認可ではないため、直接URL/APIアクセス時は引き続きサーバーが許可を確認する。

## 4. ダッシュボードの情報順序

1. 管理対象名、現在の公開/利用状態、会員数。
2. 今日の対応事項。未処理承認、配信失敗、期限などを重要度順に提示し、対象操作へ直接移動。
3. 主要な利用実績。サービスに合う3〜5指標と集計期間。研修にSNS投稿件数を主指標として表示しない。
4. よく使う操作。会員、配信、通常設定など、該当する業務へのリンク。
5. 未完了の場合だけ開始準備。任意資料の不足と、実行できない必須条件を区別する。
6. 詳細管理への入口。

開始準備の全項目を毎回最上部へ並べない。現在の`buildServiceOperationActions`と`buildServiceLaunchReadiness`を再利用し、実行拒否と参考情報の種別を明示する。安易な新しい「準備完了」永続フラグは作らない。

集計できない場合は「取得できません」を表示する。0人・0件・正常と扱わない。補助集計が失敗しても主要な設定リンクは表示できる構成を目指し、認可・稼働状態・契約の取得に失敗した場合は許可があると推測しない。

## 5. 通常操作のフロー

### 基本設定と配信時刻

ダッシュボード→サービス設定→変更→保存。保存後は同じ画面で成功・適用値を表示する。reason、証跡、対象IDは入力させない。サーバーは現在の対象と権限を再確認し、自動で業務種別・差分・操作者を既存記録へ残す。

他画面を開いて反映確認をすることを通常の必須手順にしない。競合時は差分と最新値を示し、保存済みの別変更を勝手に上書きしない。通信結果が不明な場合は、保存済み状態の取得または同じ操作の再確認へ導く。

### 会員の通常対応

ダッシュボードの要対応→会員詳細→許可された対応→結果表示。既存の招待・再送・参加状態表示を再利用する。ロール変更・契約・利用権の剥奪は通常案内と別に扱い、重要操作の差分確認を適用する。

### 学習設計の承認

研修の要対応→内容を読む→対象版と影響を確認→「この学習設計を承認」1回。現在の定義取得と保存後の照合はシステムが実行する。詳細欄には必要時だけ版・取得元・自動記録を表示する。

「承認した学習内容」と「研修を開始できる状態」は別表示とする。承認ボタンでAI呼び出し、Pilot開始、受講者登録、課金、配信を連鎖実行しない。保存が受理されても最新状態の照会が失敗した場合は「承認を受け付けました。現在状態を確認中」と表示し、失敗と断定して新規承認を繰り返させない。

### 一斉配信

本文・対象を編集→対象人数と差分を自動取得→送信先/予定時刻/利用枠を一画面で確認→送信確定1回。確認の裏で対象人数や権限が変化した場合は送信を止め、変更点だけを再提示する。既存Job・recipient判定・冪等性を再利用し、別の送信基盤は作らない。

### OEM導入と運営

本部の既存OEM一括作成→非公開の標準環境と招待を発行→OEM管理者が自分の団体/Serviceで設定。標準値の根拠と上限の出所を表示し、同じ団体名・連絡先・Brandを別画面へ手で転記させない。請求先や法的名称が実際に異なる場合は、同じ値で上書きせず個別編集できるようにする。

## 6. 詳細情報の配置と文言

- 通常画面では「保存しました」「承認済み」「配信対象が変わりました」のように、業務上の状態を表示する。
- UUID、SHA、revision、reviewDigest、証跡キー、Provider設定名は、読み取り専用の詳細領域へ。必要な問い合わせ番号はコピーできる表示にする。
- 内部Flag名を運営者への主な解決手順にしない。「本部でAI利用枠の確認が必要」「このサービスは停止中」のように不足条件・対応者・対象操作を示す。
- 一般会員の権限拒否とDB障害を同じ404で説明しない。秘密値やraw exceptionは画面に出さない。
- 変更理由は自動の操作名と差分で足りる通常操作からなくす。金銭補正・権限変更・例外対応の説明は、必要性を確認して任意メモまたは重要操作の記録へ残す。

## 7. PCとスマートフォン

PCは左の業務分類と対象名、右に主操作。スマホは同じ情報順序で1列にし、カテゴリ移動を折りたたむ。秘密設定・詳細履歴を初期展開せず、主要な保存/確定と結果を探しやすくする。

受け入れ幅は390×844および1280×800を基本とし、320px幅でも主操作が隠れないことを確認する。長い日本語サービス名・エラーメッセージ、フォーム内のselect、表の横scroll、ソフトキーボード表示を検証する。

ラベルとinputの対応、キーボード操作、focus、保存中の二重送信防止、aria-liveによる結果通知を維持する。重要操作の差分確認はwindow.confirmとpromptの連続ではなく、同じ画面内で内容を読める一つの確認にする。

この段階では新しい見た目のフレームワークや全画面置換は不要。既存のAppShell/PublicShell、settings-card、レスポンシブCSSとコンポーネントを再利用する。

## 8. 操作数と測定方法

監査の静的基準に対し、通常保存1回、技術情報入力0、管理ホームから学習設計承認へ1遷移を目標とする。単純な入力focusを「クリック削減」に水増ししない。

各PRで同じ初期状態・同じタスクのPC/スマホ操作を記録し、画面遷移数、送信回数、確認回数、技術入力数、文字入力が必要な業務項目数を比較する。ネットワーク失敗時と権限失効時は正常系とは別集計にする。計測のための新しい個人行動ログやAnalytics台帳は追加しない。
