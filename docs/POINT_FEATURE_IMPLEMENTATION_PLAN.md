# ワタシワークス 行動ポイント機能 実装計画

更新日: 2026-08-29

状態: Phase P-0 設計レビュー待ち

入力仕様: `WATASHI_WORKS_POINT_FEATURE_SPEC_V1_0.docx`

## 1. 目的

LINE通知から企画確認、採否判断、コピー、投稿完了までの継続行動を促すため、ワタシワークス内だけで利用できる「ワタシポイント（WP）」を追加する。ポイント機能は既存行動の正本ではなく、既存行動イベントから派生する疎結合なインセンティブ機能とする。ポイント処理が停止しても、企画閲覧、コピー、投稿完了を止めない。

## 2. 既存機能との境界

- 行動の正本は既存の`MissionActivity`、`MissionDecision`、`PostRecord`とする。
- `VIEWED`、`ACCEPTED`、`REJECTED`、`COPIED_*`、`POSTED`をポイント判定へ再利用する。
- ポイント処理用Eventは既存行動を複製する正本ではなく、冪等なInbox／処理記録として扱う。
- 投稿本文、Prompt、OwnerKnowledge、BunshinMemory、LINE user IDをポイント関連テーブルへ複製しない。
- 販売プランの`Credit`は画像・動画等の原価と利用権を管理する単位、WPは本人の継続行動を促す特典単位であり、同じ残高・台帳・APIへ混在させない。
- WPは現金、暗号資産、電子マネー、外部ポイント、報酬債権ではなく、購入・換金・譲渡を提供しない。

## 3. 適用境界と設定合成

企業契約境界は既存Workspace／Groupと販売プラン基盤との対応を後続ADRで確定する。全Use CaseでWorkspace、Group、Membership、Userをサーバー側検証し、Group管理者へ個人の通常投稿、人格、Memoryを公開しない。

設定候補は次の優先順で合成する。

`SYSTEM_DEFAULT → USER_CATEGORY → CONTRACT_PLAN → WORKSPACE/TENANT → GROUP → CAMPAIGN → USER_RESTRICTION`

- 上位の禁止を下位で解除できない。
- 数値上限は適用対象のうち最も厳しい値を採用する。
- 個人設定は制限、問い合わせ、不正対応を原則とする。
- 複数Group所属時は現在選択中のGroupとCampaignを明示し、暗黙に混合しない。

## 4. 台帳・残高・費用負担

- 残高を直接増減せず、追記型台帳から再計算できるようにする。
- 利用者には共通WP残高を表示する。
- 台帳には付与元、費用負担者、Workspace、Group、Campaign、Rule Version、有効期限、冪等Keyを固定する。
- 失効日が早い利用可能付与から消費し、`PointConsumptionLink`でどの付与を消費したか確定する。
- 企業負担WPを別企業限定の特典へ誤使用できない資格判定を行う。
- 訂正は`REVERSAL`、技術的失敗の返却は`REFUND`、使用済み付与の回収は`RECOVERY`を追記する。
- 残高を負数にしない。回収不能額は`recoveryDue`として記録し、解消まで交換だけを停止する。

## 5. MVP範囲

### 含める

- ユーザー単位のポイント口座と追記型台帳
- 付与、利用、取消、返却、失効
- 日次、週次、初回達成ルールと版管理
- 冪等性、二重付与防止、同時消費制御
- 残高、履歴、失効予定、週間進捗
- 画像生成1回、追加企画生成との交換
- 技術的失敗時の予約解放または自動返却
- システム管理者のルール管理、手動調整、監査、CSV
- Group単位の利用可否、承認済み追加付与、企業独自特典
- Feature Flag、予算上限、異常検知、緊急停止

### 含めない

- 現金、暗号資産、電子マネー、外部ポイントへの交換
- ポイント購入、他ユーザーへの譲渡
- アフィリエイト報酬、物品、ギフト券、抽選、ガチャ、公開ランキング
- SNS APIによる投稿内容の自動検証
- 動画生成との交換

## 6. 初期ルール候補

| 行動           |                初期値 |
| -------------- | --------------------: |
| ログイン       |                   OFF |
| 企画の初回確認 |               1WP／日 |
| 投稿完了       |               5WP／日 |
| 週3回投稿達成  |              10WP／週 |
| 画像生成1回    |              50WP消費 |
| 追加企画生成   |              30WP消費 |
| 日次最大獲得   |              10WP目安 |
| 有効期限       | 獲得から180日後の月末 |

初期値はハードコードせず、版管理されたRuleとFeature Flagで変更する。Group追加付与はSUPER_ADMIN承認を必須とし、Group管理者の自己付与を禁止する。

## 7. 実装フェーズ

### P-0: 設計確定・文書PR

- 本計画、ロードマップ、Decision Logを更新する。
- Activity対応、Group／Workspace境界、Creditとの分離、消費順、回収方針を確定する。
- 利用規約、失効、退会、企業特典の責任主体を人間レビューする。

完了条件: コード、Schema、Migrationを変更せず設計レビューが承認される。

### P-1: Core Persistence

- `PointAccount`
- 追記型`PointRuleVersion`
- `PointTransaction`
- `PointConsumptionLink`
- `PointProcessingEvent`
- `PointRuleBudget`
- DB一意制約、CHECK、部分一意index
- Repository、Use Case、Isolation／Concurrency Test

完了条件: 並行処理、再送、同時消費でも二重付与と負残高が発生しない。

### P-2: 行動連携

- 既存Activity／PostRecordから付与判定するProcessor
- 初期対象は企画初回確認、投稿完了、週間達成
- タイムゾーン、日次／週次境界、再処理、DLQ
- ログイン付与はFeature Flag OFF

### P-3: 利用者API・画面

- 残高、履歴、失効予定、獲得方法、週間進捗
- 獲得時の分かりやすい日本語表示
- 本人以外の残高と履歴を取得できない認可
- ポイント障害時にも既存画面を利用できる縮退動作

### P-4: 交換・利用権

- 共通交換カタログ、交換確認
- 予約、確定、解放、返却
- 画像生成および追加企画生成の利用権
- Provider受付前の解放、最終失敗時の補償返却

### P-5: Group・企業機能

- Groupごとの利用可否と上限
- Group付与Ruleの下書き・承認、Campaign追加付与
- 企業独自特典、手動履行状態、Group管理者向け集計
- 自己付与禁止とGroup／Workspace isolation

### P-6: 管理・運用

- システム管理画面、手動付与・取消・返却、理由必須Audit
- CSV、予算監視、異常検知
- 残高再計算・照合、失効・失効予告Job
- Feature Flag、緊急停止、再処理・復旧手順

### P-7: 30人限定検証

- Feature Flagで対象者だけに4週間公開する。
- 投稿完了率、継続率、交換率、原価、不正率を計測する。
- 投稿完了は本人の自己申告であることを明示する。
- 外部検証結果に基づき、付与数、有効期限、交換必要WPを調整する。

## 8. 必須テスト

- 同一イベント再送で二重付与されない。
- 同時交換でも負残高にならない。
- 別User、別Group、別Workspaceの残高、履歴、特典を参照できない。
- Group管理者が個人の通常投稿、人格、Memoryを取得できない。
- 上位で禁止された機能を下位設定で有効化できない。
- 期限切れ・停止中Ruleで付与されない。
- 画像生成失敗時に消費が確定しない、または一度だけ返却される。
- ポイント機能停止中も企画、コピー、投稿完了を利用できる。
- 台帳再計算と残高Read Modelが一致する。

## 9. 人間確認事項と停止条件

P-0承認前にSchema、Migration、API、Job、管理画面を実装しない。次を人間レビューする。

1. 企業別費用負担と共通残高の利用規則
2. 企業契約境界をWorkspaceとGroupのどちらへ対応させるか
3. 失効、退会、回収不能時の利用規約
4. 企業独自特典の責任主体
5. 画像生成と追加企画生成の実原価
6. 30人検証の対象者とFeature Flag
