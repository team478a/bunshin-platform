# 企業・グループ型広告サービス 監査と最小改修計画（2026-11-12）

対象: ワタシワークス bunshin のハッシー企業・グループ型広告サービス。企業・団体が、代理店・販売店・従業員・会員へ広告キャンペーンを提供する「グループ型AI情報発信サービス」。

監査基準: `main` `3d356e0`（PR #1500）。この基準より古いミラー（PR #530時点）で行った監査は破棄し、同じ観点を最新mainのコードと使い捨てPostgreSQLで再確認した。

## 0. 前提と作業境界

- 既存のWorkspace、Service（Group＋`ServiceConfiguration`）、`GroupMembership`、Bunshin、SOCIAL Capability、Campaign、Product Pack、External Tracking、Posting Approval、OEM基盤を再利用する。
- 新しいSNS基盤、汎用AIエージェント、新規DBテーブル、ワークフローエンジン、課金基盤、別のグループ階層モデルは追加しない。
- 千ノ国メディア固有のブランド・名称・ルールを他Serviceへコピーしない。マナベルスタイル連携は任意の将来連携とする。
- 本書の作業では、Production設定変更、実広告配信、SNS投稿、課金、顧客データ変更、PRマージ、本番デプロイを行っていない。

## 4. 操作フロー（目標）

### 企業管理者

1. 商品情報: `/s/{slug}/manage/product-packs` で商品パックを作成し、版を公開する。
2. キャンペーン: `/s/{slug}/manage/campaigns` で商品版を選んで作成し、公開する。生成制御の数値は初期値のまま（詳細設定は必要時のみ）。
3. 確認ルール: `/s/{slug}/manage/post-approvals` で、商品投稿をコピー前に確認するかを決める。
4. 参加者: 参加者と参加状況を確認する（PR-4で導線整理）。
5. 確認: 確認待ちの本文を読み、承認または見直し依頼をする。
6. 成果確認: 参加者数、投稿案生成、採用、コピー、投稿完了（本人申告）、外部URL利用を確認する。計測できない値は表示しない。
7. 中止: キャンペーンを中止すると、未コピーの投稿案はコピーできなくなる（PR-1）。

### 参加者（Service分身）

1. Serviceへ参加し、分身を作る（既存）。
2. 参加募集を見て参加する（PR-2）。参加時に、そのCampaignの商品パックを自分の分身へ割り当てる同意を同じ操作で行う（PR-2）。
3. 毎日の投稿案を受け取る（既存）。
4. 企業の確認が必要なServiceでは、確認が終わるまでコピーできない（既存）。
5. 別の案を使う場合、WPを使う前の確認文で「確認がやり直しになる」ことが分かる（PR-1）。別案を初めて選ぶと確認依頼が別案本文で出し直される（PR-1）。
6. コピーして自分でSNSへ投稿し、投稿したことを本人申告する（既存。PR-5で表記を明確化）。
7. SNSへの公開は本人の操作・承認で行い、企業の確認はこれを代行しない。

## 6. A/B分離テスト設計

各企業は独立した組織Workspace、Group、ServiceConfiguration、SERVICE_ADMINとPARTICIPANT、groupId付き分身、公開商品版と割当、OPENのCampaign、参加ACCEPTEDを持つ。別のグループ階層モデルは追加しない。

| 観点            | 確認内容                                                                                                                                    | 実装 |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| 承認            | B管理者はAのCampaign一覧を取得できない（FORBIDDEN）。B参加者はAの投稿案のコピー可否を取得できない（null）。Bの確認依頼はAの操作で変化しない | PR-1 |
| Campaign状態    | Aの中止はBの投稿案のコピー可否に影響しない                                                                                                  | PR-1 |
| 参加者・参加    | B参加者はAのCampaignへ参加できない。Aの参加者一覧にBの参加者が出ない                                                                        | PR-2 |
| 商品・素材・URL | Aの商品版・素材・外部計測URLをBの分身へ割り当てられない                                                                                     | PR-2 |
| 実績            | Aの集計にBの生成・採用・コピー・投稿完了が混ざらない                                                                                        | PR-5 |
| ブランド        | Aの表示名・運営者名・ロゴがBの画面・投稿案に出ない                                                                                          | PR-5 |
| 利用権限        | AのGroup Feature割当がBに効かない                                                                                                           | PR-5 |
| LINE配信        | AのLINE配信対象にBの参加者が含まれない                                                                                                      | PR-5 |

## 7. 本書作業での検証（非本番）

- 使い捨てPostgreSQL（ローカル、`bunshin_disposable_*`）に全migrationを適用し、`db:assert-ready` が通ることを確認した。
- 企業A/Bの独立Service（実データではない合成データ）で、PR-1の統合テストを修正前のコードに対して実行し、P0-3・P0-4のテストが失敗することを確認した（再現）。
- 同じfixtureで、Service分身の `listAvailable` / `decide` が `NOT_FOUND`、参加レコードがない場合の計画が0件になることを確認した（P0-1の再現。一時的な確認で、テストとしてはコミットしていない）。
- 千ノ国メディアを含む既存Serviceのデータには触れていない。ブラウザでの画面操作は実施していない。

## 8. 一般販売 Go / No-Go

**判定: No-Go（PR-1マージ後もNo-Go）。**

- PR-1で、確認済み本文以外のコピーと、中止後・参加条件変更後のコピーは止まる。
- ただしService参加者がCampaignへ参加する手段（P0-1）と、Service分身への商品割当の画面（P0-2）がないため、企業Serviceで1キャンペーンを画面だけで通せない。
- Go条件: PR-1〜PR-2のマージと本番反映、PR-3の確認ルール整合、非本番の独立企業Serviceで画面から1キャンペーンを通した手動検証の記録、本番反映の証拠（production SHAと確認記録）。PR-4・PR-5は初期運用で並行して進めてよい。
