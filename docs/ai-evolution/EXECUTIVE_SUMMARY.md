# 経営判断用要約: AIが進化するほどワタシワークスも進化する

2026-10-09 / 最新main `5b4957f1f2a983aa571ebd72d73ec4d67c3bbe84` の監査。**今回は文書のみ。本番・DB・モデル設定を変更していない。**

## 結論

既存基盤は再利用できる。新しい汎用AIプラットフォームを作り直す必要はない。ただし「モデル名を変えるだけで安全に進化できる」状態にはまだ不足がある。AIを更新する前に、品質・安全・原価を比較できる小さい仕組みを足すことを推奨する。

## 既にあるもの

- 外部AIの設定・接続検査・停止・予算、利用量や原価の記録、用途別のAI接続。
- ハッシーの企業情報、投稿案、週間計画、採否・不採用理由・実績を次の提案へ渡す経路、継続支援。
- マナベルスタイルの本人確認済み学習目標・計画、課題・評価・次の学習、最初の成功と本人能力の証拠、限定Pilotの安全対策。
- OEMの提供ルールと課金の計測。ハッシーは無料提供なら実測利用、有料提供なら登録。マナベルスタイルは有料提供・登録基準。

主要な既存テスト945件がローカルで成功。実際の本番学習・外部AI品質・OEM請求の成功を945件で保証したという意味ではない。OEM登録課金の新実装はmainにあるが、調査基準のproduction branchへ未反映である。

## 足りないもの・最優先3項目

1. **新しいAIに変えても品質が落ちないか比較する基準。** ハッシーの事実・提案品質と、マナベルスタイルの学習評価は別の基準を持つ。
2. **必要な処理だけを安全に新モデルへ変更する仕組み。** 現在は共通設定の変更が複数機能へ広がり、通信の時間制限も処理ごとに差がある。
3. **正確な原価把握。** 原価が不明な処理や、同じ呼出しを二重集計するリスク、OEMごとの帰属を整理する。

その後、ハッシーで「提案が採用され継続できたか」、マナベルスタイルで「本人が別の題材でも自力でできたか」を実証する。良い完成品ができただけで本人の能力が上がったとは判定しない。

## 推奨順序と負担

品質比較の基準 → 通信安全性 → 小さいモデル互換ルール → 原価計測の信頼性。最初の4つは合計約7–11開発人日を仮置きする。サービス改善の検証は別で約4–8人日。権限待ち・実AI費用・本番移行・運用期間は含めず、最初の小PRの実績で見直す。

Dots/Codexを使う改善運用は、既存の問題整理と人間レビューを再利用できる。最初からAPI接続や自動開発を作らず、匿名化した指示を人間が渡す方法でよい。Dotsは製品の特定が未回答で、直接API利用を仮定しない。Codexの公開仕様は確認したが、本システムへの接続は未実装。

## 影響とリスク

全面改修より小PRを選ぶ。現在の停止・認可・100人上限・費用制限、既存利用者の動作、OEM課金ルールは維持する。モデルを一括変更すると他サービスにも影響し得るため、品質確認後の限定切替と戻し方が必要。

不明な原価を0円にしたり、本人の自己申告を習得済みと断定したり、顧客の相談・成果物を外部開発AIへ渡したりしない。AIによる修正案、実装、PR、merge、本番deployはそれぞれ人間の判断を分ける。
