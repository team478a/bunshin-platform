# サービス内管理者権限 Core 実装報告

## 目的

サービスの契約責任、日常管理、コンテンツ作成、一般利用を分離し、将来BLOGなどの機能が増えても管理者へ不要な権限を与えない基盤を作る。

## 追加した業務ロール

- `SERVICE_OWNER`: 契約、管理者、全設定を扱うサービス責任者
- `SERVICE_ADMIN`: 参加者と日常運用を扱うサービス管理者
- `CONTENT_EDITOR`: 商品、公式資料、投稿企画等を扱うコンテンツ担当者
- `PARTICIPANT`: 本人向け機能だけを使う一般利用者

既存の`GroupRole`は互換性のため削除しない。サービス責任者とサービス管理者は既存処理では`MANAGER`、コンテンツ担当者と一般利用者は`PARTICIPANT`へ対応させる。

## 既存データの移行

- サービス作成者に対応する既存管理者を`SERVICE_OWNER`へ移行する。
- その他の既存管理者を`SERVICE_ADMIN`へ移行する。
- 既存参加者は`PARTICIPANT`のまま維持する。
- 新しいサービスの作成者は作成時から`SERVICE_OWNER`にする。
- 管理者招待から参加した利用者は`SERVICE_ADMIN`にする。

## 安全境界

- 変更できるのは有効な`SUPER_ADMIN`または同じサービスの`SERVICE_OWNER`だけとする。
- Workspace、Group、MembershipをRepositoryで再検証する。
- 最後の有効な`SERVICE_OWNER`は降格できない。
- ロール変更時は既存Group Roleも整合させる。
- 変更理由、変更前後、実行者、時刻を既存Membership Auditへ保存する。

## 次の実装

S2でサービス責任者向けの権限管理API・画面を追加する。S3では、コンテンツ担当者が商品・公式資料・企画だけを扱えるよう、各管理機能へ用途別の認可を接続する。S3完了までは`CONTENT_EDITOR`を既存管理機能の管理者として扱わないため、過剰権限は発生しない。
