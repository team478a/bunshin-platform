# 毎朝の運用まとめメール 設計案

作成日: 2026-10-20

対象: ワタシワークス全体の運用状況

状態: 段階1設計。田中の確認待ち。実装・本番送信は未実施。

## 1. 目的と境界

毎朝1通で前日の運用状況を確認できるようにする。異常なしの日は件名と本文1行にし、注意・異常がある日はその項目を先頭にして管理画面へつなぐ。異常なしの日も送信し、「未着」と「異常なし」を区別する。

本機能は読み取り専用の集計とメール送信だけを行う。利用者データ、設定、ジョブ状態を変更しない。本文には氏名、LINE ID、メールアドレス、利用者ID、投稿・会話・問い合わせ本文、金額、取引先名、生のエラー文を含めず、件数・サービス名・処理名・エラー分類だけを使う。OEM請求は催促・回収・未回収の件数だけとする。AIによる要約・分析、LINE通知、新しい外部サービスの導入は対象外。

## 3. 提案する基本フロー

1. Vercel Cronが内部routeを呼び、`CRON_SECRET` を検証する。環境はproductionだけを対象にし、環境変数 `OPS_DIGEST_ENABLED` が文字列 `true` でなければ集計・送信せず、機能OFFとして安全に終了する。
2. JST日付を基準に対象日を一意に決める。集計対象は前日JST 00:00以上・当日00:00未満の半開区間とし、UTCへ変換して各DB queryへ渡す。日時境界テストを置く。
3. `GetAdminAlerts` を呼び出し、既存アラート判定と `alert.href` をそのまま使う。前日イベント集計は別Collector群で追加し、各Collectorは `OK` / `UNAVAILABLE` / `NOT_APPLICABLE` の状態を返して0件・未実行・取得失敗を区別する。
4. 登録済み宛先へテキストメールを送信する。異常なしでも必ず送信する。有効化されていない場合や宛先設定が不完全な場合は送信しない。
5. 送信結果を日付・環境単位で永続化する。claim前にすでに送信済みならskip。処理中claimはlease/期限を持たせる。Resendの `idempotency-key` も併用するが、プロバイダーの重複抑止だけに依存しない。

## 4. 送信時刻・判定・文面

### 4.1 時刻・対象日

- 希望時刻は毎朝07:30 JST。時間帯はIANA `Asia/Tokyo` を明示する。
- 設定変更可能な値 `OPS_DIGEST_SEND_TIME_JST`（`HH:mm`）を設計する。
- VercelのCron scheduleはUTCで静的に宣言されるため、実行トリガーと可変時刻の両立を段階2で決める。推奨はCronを短い間隔で起動し、routeが設定時刻・JST日付・送信済み状態を確認して一致時だけ処理する方式。ただし実行頻度・プラン上限・他cronへの負荷を事前確認する。固定 `22:30 UTC` だけにする場合は時刻を環境設定だけで自由変更できず、`vercel.json`変更と再デプロイが必要になるため、要件を満たすか田中の承認を得る。
- 対象期間は前日JST 00:00:00以上、当日JST 00:00:00未満。境界はUTCに変換してqueryする。毎時LINE監視などは前日件数と送信時点の状態を分ける。
- weekly/monthly等の実行日でない集計は0件扱いにせず「本日対象外」とする。該当処理が実行予定日なのに実行記録を確認できなければ「異常」または取得失敗にする。

### 4.3 メール文面

テキストメールを使い、本文は既存の許可されたラベル・数値・固定リンクで組み立てる。生のerror message、利用者由来の文字列、任意のDB本文をテンプレートへ渡さない。

**異常なし**

- 件名例: `【ワタシワークス運用】10/19 異常なし`
- 本文: `前日の定期処理・配信・通知はすべて正常でした。管理画面：<管理画面URL>`

**注意・異常あり**

- 件名例: `【ワタシワークス運用】10/19 異常2件・注意1件`
- 本文順: 1) 異常（項目名・件数・管理リンク）、2) 注意、3) サービス別件数一覧（正常含む）、4) 取得元なし/取得失敗、5) 送信時点の状態。
- 取得元なし、取得失敗、対象外、未実行はそれぞれ表示を分ける。
- 表示件数は「人」ではなくrecord / recipient / broadcastなど、明示した単位を添える。

### 4.4 管理画面リンク

### 4.5 集計失敗・送信失敗・前日未送信

- Collectorまたはメール送信の失敗は、例外内容を保存せず、固定されたerror category、日時、対象日、環境、処理段階だけを運用記録へ残す。
- Alert Centerは正本を表示時に読むため、それだけではdigest処理自身の失敗履歴を記録できない。既存Jobの `DEAD` / `lastErrorCategory` にdigest失敗を残せるかを段階2で確認し、不適合なら小さな専用運用記録の必要性を田中へ提示する。
- 送信失敗が発生した日は「送信済み」にしない。安全な再試行か、運用者が再実行するかを送信台帳の状態遷移と合わせて決める。一定時間以上の同時実行claimは期限付きleaseで回復可能にする。
- 当日のメールで前日のJST日付に送信済みrecordがなければ「前日のまとめが送信されていません」と表示する。初回導入前の履歴がない期間は「履歴開始前」とし、未送信異常と誤判定しない。
- メール送信自体が止まるとメール通知は不可能なので、外部死活監視サービスは選択肢として比較するだけで、追加・設定はしない。

### 4.6 ドライラン

管理者限定の「今日のまとめをプレビュー」を用意する。Cronと同じcollector・判定・テンプレートを使い、メール送信・送信台帳の状態変更は行わず、本文・件名・状態・数値・リンクだけを画面へ返す。プレビュー時刻とJST対象日を明示する。個人情報が返らないテストを通し、本番での送信開始前に田中が内容を確認できるようにする。

## 5. 段階2の実装範囲とPR分割案

段階2もmigration作成は禁止。既存の正本とJob/監査記録だけで要件を満たせない場合は、migrationを作らず、理由と追加型migrationの案を別途提出して許可を待つ。

1. **PR-1 読み取り集計**: applicationに日次のCollector契約・3段階判定・設定値1か所を追加し、databaseに各正本から読む読み取りadapterを追加。`GetAdminAlerts`は再利用。個人情報・本文をCollector境界へ出さない。
2. **PR-2 送信・Cron・記録**: `apps/web/src/email/` に既存Resend設定を使うdigest送信adapter、`apps/web/app/api/internal/` にCRON_SECRET保護route、`vercel.json`にCron追加。既存Jobによる日次claim/状態記録が安全かを先に証明し、不適合なら別途migration許可を得る。`OPS_DIGEST_ENABLED` の未設定/falseは送信しない。
3. **PR-3 管理者Preview**: 管理者権限のPreview画面とAPIを追加し、送信・状態書込なしで件名と判定済み文面を表示する。

PRは個別Draftと日本語報告で提出し、前PRのマージ・田中確認後に次へ進む。Secretsや本番の宛先値はコード・報告へ記載しない。

## 6. 段階2の受入テスト

- 全対象正常時は件名が「異常なし」、本文が1行。
- 異常・注意が混在すると、件名の件数、異常→注意→サービス別一覧→取得状況の順が正しい。
- Collector成功の0件、取得失敗、取得元なし、対象外、予定実行日の未実行を区別する。
- JST前日境界・UTC変換・夏時間を持たないAsia/Tokyoの対象日を確認する。
- 同じ日付で同時/連続2回起動しても送信は1通。送信前失敗、Resend timeout、送信応答不明、lease切れを含む競合を確認する。
- 件名/本文にemail、LINE ID、UUID等の利用者ID形式、投稿・会話・問い合わせ本文、生エラー文字列を含めない。
- `OPS_DIGEST_ENABLED` 未設定/falseではメールproviderを呼ばず、集計対象の利用者データ・設定・Job状態を変えない。
- Previewは同じ結果を使うがメール送信・送信済みrecord更新を行わない。
- 既存Alert Centerの判定・画面、既存メール/LINE通知、cronの実行・送信動作に回帰がない。

## 7. 田中に確認してほしい点

1. 宛先は既存 `RESEND_ADMIN_ALERT_TO`（またはDB管理の管理メール宛先）と共用するか。運用まとめだけ別担当へ送る場合は `OPS_DIGEST_TO` 案を選ぶ。
2. 07:30 JSTを変えられる設定にするため、短周期Cronと時刻gateを許容するか。固定の22:30 UTC Cronでよいなら、時刻変更に `vercel.json`変更・再デプロイが必要。
3. production実績は未確認。表の既存判定（80/100%、24h失敗3件）をそのまま使い、それ以外の暫定しきい値・urgent問い合わせの重大度を承認するか。
4. 既存Jobが日次送信台帳として不適合の場合、migration許可が必要になる可能性を受け入れるか。Resend idempotency-key単独は1日1通保証の唯一の手段として不採用を推奨。
5. 外部死活監視サービスを追加しないまま進めるか。digestメールが止まった時の検知には外部監視または別チャネルが必要。
6. 「催促」「回収」「未回収」の集計対象日・成功定義、配信件数をrecipient/broadcastのどちらで数えるかを確認する。
7. `OPS_DIGEST_ENABLED` は未設定/falseを安全側とし、送信有効化・宛先設定は田中がproductionで行う方針を確認する。

## 8. 段階1の変更範囲と影響

変更対象は本設計書、Decision Log末尾の設計開始記録、Roadmapの本タスク1行だけ。コード、テスト、schema、migration、`vercel.json`、環境変数、Provider設定、本番設定は変更していない。したがって、段階1は既存の画面・メール・LINE・cronの動作へ影響しない。PRはDraftで提出し、田中の確認までマージも本番反映もしない。
