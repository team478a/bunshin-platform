# 管理制限の分類と簡素化方針

作成日：2026-11-03 JST。基準SHA：`7d397821b144361dcf5643dc92ce4ac95ebcb334`。監査根拠と呼び出し経路は[横断監査](ADMIN_UX_OPERATION_AUDIT.md)。本書の分類は実装提案であり、制限解除・本番有効化の指示ではない。

## 1. 判断方法

「過去仕様だから維持」ではなく、各制御が防ぐ損害、代替方法、障害時の回復を比較する。現在のコードに必要性があっても、その手入力や画面遷移まで必要とは限らない。

分類の意味：撤廃は不要な入力・確認・処理だけを取り除くこと、簡素化は業務判断を少ない操作へ集約すること、自動化はサーバーが取得できる事実・処理を担当すること、維持は具体的な損害を防ぐ境界を保つこと。一つの機能でも制御ごとに分ける。

## 3. 操作リスクの共通ルール

リスクはページ単位でなく変更したフィールドと外部作用で判定する。同じフォームでも、説明文と料金、通知時刻と大量送信、連絡先と請求先の法的変更は区別する。

| 区分 | 主な操作                                                                     | ユーザー操作                                | サーバー側で維持する処理                                                         |
| ---- | ---------------------------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------- |
| 通常 | 説明文・見た目、既存配信の時刻、通常の会員案内、一般プロフィール             | 編集→保存1回。理由欄・SHA・証跡キーなし     | 認証、現在のロール/tenant、入力、必要な競合検知、変更差分・actor・日時の自動記録 |
| 重要 | 料金・契約条件、ロール、公開対象、学習設計承認、大量配信、初回の外部配信開始 | 差分・対象・影響を表示→最終確定1回          | 承認scope/版・費用・権利の再検証、冪等性、状態更新と監査のatomicity              |
| 重大 | 大規模削除、他者への所有権/データ移管、秘密情報更新                          | 必要な再認証/確認・復旧方法を同じ流れで提示 | 専用認可、暗号化/秘密保護、復旧・停止、追跡記録。現行より弱める変更は別レビュー  |

この区分は実装者と運用者の共通基準とし、新しい汎用承認エンジンや承認テーブルは作らない。既存の各APIのvalidationと認可、共有できる最小限のUI表現をそろえる。

### 一括変更の扱い

通常項目だけなら1回保存、重要項目を含む場合だけ差分確認を1回表示する。通常項目の変更に契約確認を毎回求めない。複数の重要項目を一緒に変更する場合も、対象と影響が理解できる一つの確認にまとめる。重大操作と混在した更新は既存の専用経路で分離する。

## 4. 特に維持する制御と具体的な理由

- **tenant/Service/本人/ロール**：別顧客への閲覧・設定変更を防ぐ。メニュー非表示だけでは代用しない。
- **same-origin、検証済みセッション、秘密値の暗号化**：他サイトからの書込と資格情報流出を防ぐ。
- **revision/digest/操作ID**：古い学習設計の承認、競合更新、通信再送による重複を防ぐ。人に入力させる必要はない。
- **重要な監査と業務のatomicity**：権限・契約・承認・金銭の変更が無記録で成立しないようにする。UIから監査を隠すことと保存の無効化は別。
- **予算・利用台帳・未確定原価**：AI/画像/動画の過剰実行と費用の二重消費を防ぐ。上限の説明を改善しても予約を外さない。
- **決済Webhook・配信の冪等性**：再試行時の二重決済・二重配信・重複報酬を防ぐ。
- **本人同意と法務文書の版**：運用担当の保存簡素化で利用者の同意を代行しない。
- **緊急停止と対象限定**：一サービスの停止で無関係なサービスの設定編集まで止めない。共有Provider障害の停止は資源共有の影響として別表示する。

## 5. 技術証跡を自動化する範囲

学習設計承認GETで得られるdefinition版、revision、reviewDigestはすでに自動取得されている。追加の手入力SHAは公開コードと自動照合していないため、入力を増やすこと自体が強い保証にはなっていない。

既存APIのGETに、現在提示した内容と結びつくサーバー取得の来歴を追加する。公開コードSHAが取得できる場合はその出所も記録し、教材版・digestと同じものとして扱わない。過去の対象版をレビューする場合はその不変版を照合する。証跡キーは既存の操作ID/ProgramAuditLogの参照としてサーバーで生成する。

POSTで操作者・Service・対象版・revision/digestを再照合し、提示されていない別版を承認しない。clientの任意SHAを信頼しない。サーバーから来歴を確定できない場合は当該承認だけを明確な理由で止め、他の通常設定やサービス全体を止めない。

人間が内容を読んで承認する行為は残す。7項目を自動的にtrueにするだけの変更ではない。教育内容の承認と、AI実行の予算/モデル/参加者/本番公開の許可は別の状態・別の操作として扱う。

## 6. 監査の合理化と障害の扱い

最初に「誰が何を変えたか」の業務監査、費用・権利の正本、診断log、集計投影を区別する。後者の再生成可能な読取/表示が失敗しただけで通常設定の保存を巻き戻す構造がある場合は切り離す。ただし今回の追跡範囲では、すべての通常設定が不要な診断logにより停止しているという証拠はない。

Foundation.saveの通常変更でも同じ資源の全snapshotと関連tableを更新している点を先に見直す。無変更時のupsert・重複snapshotを減らせるか、既存利用者・exportを確認する。既存監査形式の互換性が保てなければ今回は保存形式を維持し、表示整理から行う。

非重要logの非同期化は、再生成可能か・既存Jobで処理できるか・失敗を観測できるかが確認できた処理に限定する。新outbox、汎用イベント台帳、監査統合テーブルを先回りで作らない。エラーを握りつぶして「保存済み」と表示しない。

## 7. 数値制限の変更判定

| 性質             | 例                                  | 扱い                                                                         |

| 商品UXの初期値   | Hassyの採用件数、抑制日数、成長目標 | 有効性を確認して編集可能範囲を見直す。過去snapshotは維持                     |

| 運用上の負荷制御 | 10回/60秒、同時1件、配信500件       | scopeの誤共有を直す。処理負荷/Provider制約と再試行を評価し、上限だけ消さない |
| 金銭/権利        | 予算、契約人数、決済・報酬枠        | 維持。許可変更の導線を明確にする                                             |
| Privacy          | 少人数集計の5人閾値                 | 再識別防止の具体的な目的がある。一般の「固定閾値撤廃」の対象にしない         |

## 8. 実装開始条件

低リスクの未使用理由欄撤廃・導線整理を先行できる。Flagの廃止、人数上限の変更、監査の非同期化は、現在の依存・契約・失敗時の整合性を各PRで確認してから行う。

本番設定値や使用頻度は今回取得していない。分類を根拠に利用中の機能・記録を削除しない。具体的な分割と受け入れ条件は[実装計画](ADMIN_SIMPLIFICATION_IMPLEMENTATION_PLAN.md)へ。
